## Why the old stack never flaked (parity insight)
PHP's native session handler LOCKS the session for the duration of a request: the reload's GET blocks until the in-flight `POST /preferences/theme` has finished writing the session. Spring Session JDBC has no such lock — the GET can read the session while the POST is still processing. The old stack's `assets/app.ts:41-61` also fired `void fetch(...)`, so the *client* side was already reproduced; the missing parity is the *server-side per-session serialization*.
